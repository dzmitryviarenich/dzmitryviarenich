DDA Design System

Overview

As the DDA Web Platform scaled, inconsistency grew — one-off components, no shared design–dev language, and poor accessibility.

The existing library didn’t support the platform’s scale. I built the DDA Design System from scratch, now the single source of truth across all DDA web products.

The Challenge

  • Consistency gap: multiple apps, multiple teams, no shared components or patterns. Every new feature risked introducing yet another custom solution.

  • Accessibility gaps: existing components lacked proper states (focus, active, disabled with correct cursor behavior), keyboard support, and contrast compliance.

  • Design-to-dev friction: without a shared library, handoffs were slow and implementations often drifted from design intent.

What I Built

Component Library

Created a comprehensive library of reusable components — from foundational elements (buttons, fields, checkboxes, selectors) to complex patterns (data tables, navigation bars, dialogs, timelines). Some were evolved from the existing weak library; many were designed from scratch. All built in Sketch.

Accessibility Improvements

Audited and upgraded every component for proper interaction states — adding focused states, refining disabled behaviors, ensuring keyboard navigability and sufficient contrast. For example, buttons went from four basic states to five well-defined ones including a visible focus indicator.

After

Usage Guidelines

Created comprehensive documentation on Confluence — covering design principles, interaction standards, styles, and per-component usage guidelines with states, spacing, and do/don't examples. This helped teams use elements consistently and make better UX decisions independently .

Ready-to-Use Angular Components

Held weekly meetings with developers to build a production-ready Angular component library mirroring the design system 1:1. Engineers could grab components off the shelf.

Sketch → Figma Migration

Started the system in Sketch, then led the migration to Figma — transferring the full library and establishing it as the team's primary design tool.

Workshops

Ran workshops for developers on effective collaboration workflows — including Figma ↔ VS Code and Figma ↔ JetBrains WebStorm integrations, bridging the gap between design files and code.

Impact

  • Adopted across all web surfaces: DDA Web, Admin, and Analyzers all run on the same system.

  • Reduced custom components: teams default to the library instead of building one-offs, speeding up development and maintaining consistency.

  • Improved accessibility across the platform through systematic component-level upgrades.

  • Faster design-to-dev cycles: shared language, shared components, less back-and-forth.

  • Scaled with the product: the system grew alongside DDA Web's expansion from 30% to 70%+ feature parity, supporting every new application along the way.

Reflection

Building a design system while actively designing the product creates a tight feedback loop — you notice gaps in the system in your own work first. This keeps the system practical and focused, not abstract.
